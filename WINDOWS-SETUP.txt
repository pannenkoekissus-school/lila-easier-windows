PART 4 — LILA-WS (C:\Users\Gebruiker\lila-ws, a fresh git clone)
------------------------------------------------------------------
  M build.sbt                             Windows-gated app-windows/ source dir
  M src/main/scala/netty/Pack.scala       epoll/kqueue probe -> NIO fallback
  M src/main/resources/application.conf   mongo.uri localhost -> 127.0.0.1
?? .sbtopts                               -J-Xmx2g, -Dsbt.banner=false,
                                          -Dscala.ext.dirs=C:\Users\Gebruiker\.sbt\1.0\java9-rt-ext-eclipse_adoptium_21_0_12_1
?? app-windows/reactivemongo/core/netty/Pack.scala   NIO-only shadow

  Three Windows blockers, in the order they appeared:

  1. Fatal sbt crash on startup:
         java.nio.file.InvalidPathException: Illegal char <0x0C> at index 0:
         C:\Users\Gebruiker\.sbt\1.0\java9-rt-ext-eclipse_adoptium_21_0_12_1
     sbt.bat generates -Dscala.ext.dirs="<path>" and the value arrives polluted
     with a form-feed byte. Fixed by lila-ws/.sbtopts, which sbt appends AFTER
     _JAVA_OPTS, so its clean value wins. (lila already had this line too.)

  2. The WebSocket server's own Netty: netty/Pack.scala threw when epoll was
     unavailable. Rewritten to probe epoll/kqueue by constructing and shutting
     down an event loop group, falling back to NioEventLoopGroup /
     NioServerSocketChannel.

  3. MongoDB never reachable (IsPrimaryAvailable timeouts every ~8s):
     a) "localhost" resolves to ::1 first, where wslrelay (not mongod) listens
        -> application.conf now uses 127.0.0.1. (::1 is not connectable here.)
     b) reactivemongo's own netty Pack then failed with "Only supported on
        Linux" -> the same NIO shadow lila uses was added under app-windows/.
     Final log line: Instantiated NettyPack(io.netty.channel.socket.nio.NioSocketChannel)
     and zero timeouts.

  Auth works with the existing dev data: lila-ws reads the "lila2" cookie
  (sessionId), looks it up in the Mongo "security" collection and resolves the
  user; Redis pub/sub is the lila <-> lila-ws transport, so no extra wiring.

0b) REDIS + MONGODB IN DOCKER  (skip if they already run natively)
    Both lila and lila-ws hardcode 127.0.0.1:27017 and 127.0.0.1:6379, and no auth
    is configured, so the ports must be FREE first — stop the native services
    (Windows services "MongoDB" / "Redis" or their processes) before starting these:

      # Redis
      docker run -d --name lila-redis -p 6379:6379 redis:7

      # MongoDB (data kept in a named volume, db "lichess" is created on first write)
      docker run -d --name lila-mongo -p 27017:27017 -v lila-mongo-data:/data/db mongo:8.0

    Later starts (containers persist after reboot of Docker Desktop):
      docker start lila-redis lila-mongo
      docker ps                          # both should show "(serving/publishing) 0.0.0.0:6379->6379/tcp" etc.
      docker logs -f lila-mongo          # confirm it is accepting connections

    Stop / remove:
      docker stop lila-redis lila-mongo
      docker rm -f lila-redis lila-mongo # -f also when the container is running

    Notes:
      - Data lives in the Docker volume "lila-mongo-data". Starting a FRESH container
        gives you an EMPTY database (you would have to sign up again). To keep the
        data of a previously running native mongod: stop it, then mount its dbpath
        instead of a volume, e.g. -v "<path-to-dbpath>:/data/db".
      - Delete the old data only on purpose: docker volume rm lila-mongo-data
      - Sanity check after startup:
            netstat -ano | Select-String ':27017' | Select-String 'LISTENING'
            docker exec lila-mongo mongosh --quiet --eval "db.adminCommand('ping')"

IF SOMETHING BREAKS AGAIN
  - sbt dies with InvalidPathException / "Illegal char" -> lila-ws/.sbtopts lost,
    restore it from PART 4 (same line exists in C:\Users\Gebruiker\lila\.sbtopts).
  - "Only supported on Linux" / netty epoll -> the app-windows/ shadows and the
    netty Pack rewrite (PART 3/4) were reverted; they are Windows-gated in
    build.sbt, so check that the `if os.name startsWith("windows")` block is
    still present in both repos.
  - Mongo timeouts again -> application.conf must say 127.0.0.1, not localhost
    (::1 belongs to wslrelay here); if mongo runs in docker, check `docker ps`
    and that nothing else grabbed 27017 (`netstat -ano | Select-String ':27017'`).
  - Nothing executes through the command channel -> input.txt only triggers on
    growth; append, or put an inert line such as "# cleared" first.
